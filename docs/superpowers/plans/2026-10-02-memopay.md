# MemoPay Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship MemoPay: invoice links paid in USDC/EURC on Arc mainnet through Arc's `Memo` contract, with paid status verified on-chain by the server.

**Architecture:** One Next.js App Router app on Vercel. `lib/arc` is pure viem code (config, encoding, verification, log scanning) with no DB or Next imports. `lib/db` holds SQL against Supabase Postgres via the `postgres` package. Pages call API routes; the pay page sends one `Memo.memo(...)` transaction and then posts the tx hash for server verification.

**Tech Stack:** Next.js (App Router, TypeScript), viem 2, wagmi 2 + @tanstack/react-query, zod, jose, postgres (porsager), qrcode.react, vitest. Install latest stable versions.

**Spec:** `docs/superpowers/specs/2026-10-02-memopay-design.md`

## Global Constraints

- Mainnet chain ID `5042`, testnet `5042002`. Selected by env `ARC_NETWORK=mainnet|testnet` (server) and `NEXT_PUBLIC_ARC_NETWORK` (client), same value.
- Mainnet RPC `https://rpc.mainnet.arc.io`, fallback `https://rpc.drpc.mainnet.arc.io`. Testnet RPC `https://rpc.testnet.arc.io`, fallback `https://rpc.drpc.testnet.arc.io`. Explorers `https://explorer.arc.io`, `https://explorer.testnet.arc.io`.
- USDC `0x3600000000000000000000000000000000000000` (both networks). EURC mainnet `0xbEf5f6d51CB62b58e6A8f77868681825C6fe21c1`, testnet `0x89B50855Aa3bE2F677cD6303Cec089B5F319D72a`. Memo `0x5294E9927c3306DcBaDb03fe70b92e01cCede505` (both).
- All amounts are `bigint` in 6-decimal ERC-20 units. Never use the native 18-decimal balance. Never use JS `number` for money.
- Payment tx sets `maxFeePerGas` ≥ `20_000_000_000n` (20 gwei).
- Addresses are stored and compared lowercase.
- `memo_id = keccak256(utf8("memopay:v1:" + id))`; `memoData = utf8("memopay:v1:" + number + ":" + content_hash)`.
- Amount limits: total > 0 and ≤ `10_000_000_000n` (10,000 × 10⁶). 1–20 line items; quantity integer 1–1,000; description 1–200 chars; `client_name` 1–100 chars.
- Invoice status transitions only `open → paid` and `open → void`.
- Env vars: `ARC_NETWORK`, `NEXT_PUBLIC_ARC_NETWORK`, `DATABASE_URL`, `SESSION_SECRET` (≥ 32 chars), `ARC_LOGS_CHUNK` (default `10000`), `NEXT_PUBLIC_APP_URL`.

## Review Focus

1. **Decimal input** like `"0.1"`, `"12.3456789"` or `"1e3"` typed as a unit price: must parse exactly with viem `parseUnits(x, 6)`; more than 6 decimals, exponents or negatives are rejected. Test in Task 6.
2. **Checksummed vs lowercase addresses**: a payment to `0xAbC…` must match an invoice stored as `0xabc…`. Test in Task 3.
3. **Another merchant's invoice**: merchant B must get 404 (not 403, to avoid leaking existence) on void/recheck/detail of merchant A's invoice. Test in Task 6.
4. **Payment arriving for a void invoice**: money really arrived, so the merchant must see it. Recorded as `matched=false, reason='invoice_void'`; invoice stays void. (Small extension of spec §7 reason list.) Test in Task 4.
5. **Log-scan chunk boundaries**: ranges must cover every block exactly once, including when `from == to` and when the RPC limit forces a smaller `ARC_LOGS_CHUNK`. Test in Task 3.
